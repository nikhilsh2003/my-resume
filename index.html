Engineering case studies

Three problems that show how I approach data correctness, production debugging, and AI systems over real enterprise infrastructure.

01 · FINANCIAL DATA ENGINEERING

RIBB reconciliation

Risk in Banking Book reconciliation across approximately $100B in transaction value. The core challenge was reconciling information that lived across systems with different purposes and semantics.

  • Used metadata/configuration tables describing how ~100 feed groups were expected to run.
  • Correlated run-instance and transaction tables containing execution status and results.
  • Compared those results against the final report in Impala and the business-language report in SQL Server used by the risk calculation engine.
  • Reduced manual adjustment effort by 60%, measured using the average amount of adjustments required.
  • One adjustment type was intentionally outside the handled scope and represented 40% of transactions — an important limitation of the result.

02 · DEVELOPER INFRASTRUCTURE

Production debugging MCP

An AI-assisted workflow used by SL3 production support to turn an error report into an evidence-backed proposed code change while keeping human review in the loop.

  • Collects production traces and relevant diagnostic context.
  • Analyzes repository code and traces the failure toward a root cause.
  • Generates candidate fixes and explains why the preferred fix is stronger than alternatives.
  • Creates a pull request containing the proposed change and detailed root-cause/fix justification.
  • Adopted by SL3 support, significantly reducing RCA and SLA-resolution timings without autonomous production deployment.
Production Error→Context + Traces→Code Analysis→Root Cause→Proposed Fix→PR + Human Review
03 · ENTERPRISE AI

Database MCP across heterogeneous sources

The difficult part was not connecting an LLM to a database. It was making enterprise data understandable enough for an LLM to choose the right context and generate useful queries.

  • Exposed internal metadata and configuration information through MCP.
  • Connected run-instance and transaction-status data with report outputs from Impala and SQL Server.
  • Used RAG/context retrieval to ground LLM-driven query generation in the meaning and role of each source.
  • Designed the workflow around heterogeneous schemas, business terminology and the need for controlled access to internal financial data.
User Intent→Context Retrieval→Source Selection→Query Generation→Enterprise Data

How I think about engineering

Make the system understandable before making it clever.

I care about what happens when traffic rises, dependencies fail, data changes shape, or an operational workflow breaks at 2 AM. That usually means starting with the data flow and failure modes, then choosing the simplest architecture that makes correctness and recovery explicit.

I am particularly interested in distributed systems, backend performance, financial data, developer infrastructure, and the boundary between AI reasoning and production software.
